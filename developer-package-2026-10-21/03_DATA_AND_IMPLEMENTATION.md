# Контракт и реализация

## Подтвержденное устройство baseline

- `models.Profile`: extra=forbid; arrival_status — только presentation; study_status не содержит admitted; campus_id по умолчанию main. Даты entry_at и arrival_at различаются.
- `EventInput`: подтверждение, occurred_at и idempotency_key; исправления через supersedes_event_id. Виза требует visa_expiry, регистрация — residence_type и registration_expiry. Срок документа не должен предшествовать выдаче. Передача этих событий без обязательных полей сейчас невалидна.
- `TaskStatus`: not_started / in_progress / completed. «Подано/ожидаю» не существует как универсальный текущий enum.
- `RuleDraft.family` ограничен M01–M10; source_type различает official, employee_confirmed и demo_model. Единица срока уже имеет calendar/working/hours/unspecified.
- UI и presentation используют server tasks; engine/service отвечают за применимость, эпизоды, ключи, пересчет, историю и outbox. Их полномочия сохранить.

## Необходимые изменения

| Потребность | Предлагаемая модель | Требование |
|---|---|---|
| До начала занятий | Отдельный admitted/аналогичный статус | Обновить schema, support rules, формы, RU/EN и тесты; не считать автоматически active |
| Готовность приглашения/визы | Подтвержденные факты либо workflow progress с provenance | Не хранить только локально; различать ожидание и получение |
| Декомпозиция M01 | Семантические дочерние задачи с независимыми ключами | Проверить поддержку catalog/service/UI; не добавлять family без изменения строгой схемы |
| Частичная передача | Результат процесса/чек-лист | Не completed и не дублирующая задача |
| Подача/ожидание | Workflow status отдельно от eligibility | Старые user_status сохраняют совместимость; отображение и причины завершения однозначны |
| Получен документ, срок неизвестен | Отдельный reported-result факт с missing expiry либо явное расширение события | Не обходить текущую валидацию; не выдумывать expiry; не запускать продление без нужного якоря |
| Источники | section/path hint и purpose | Версионировать вместе с содержанием; RU/EN для продуктового текста |
| Демо-единицы | Отдельный demo override с происхождением | Не мутировать официальный snapshot |

Конкретные новые имена API в пакете не утверждены. До изменений описать небольшой контракт и миграцию в репозитории, затем реализовать их согласованно. Не вводить параллельный JS eligibility engine из прототипа.

Особенно важно: дата выдачи/получения и дата окончания — разные факты. Не использовать expiry как occurred_at. При позднем входе неизвестные даты прошлого не заменять сегодняшним днем. Известное состояние можно отразить как первоначально сообщенный факт с отдельным временем записи и неизвестным временем события; семантику определить явно.

## Связь семейств

M01 → процессы подготовки P1–P3; общую задачу исключить из дублей, если появились дочерние. M02 → проверка фактических въездных документов после въезда; отдельная подготовка поездки до него. M03 → комплект в вуз; M04 → учет по жилью. M05/M06/M10 сохраняют проверки применимости, не становятся выполненными от «вопрос отправлен». M07/M08 — циклы продления в учебном сопровождении. M09 остается оркестрацией последствий, не дублирует затронутые действия.

Новые данные подключить к сохранению, редактору правил, валидации публикаций, preview/diff, переводу и OpenAPI. Дочерние task keys должны включать стабильный смысл, эпизод/цикл там, где он нужен. Изменение версии правила не означает новую процедуру само по себе.

## Миграция и совместимость

- Старое completed общей M01 не переводить во все completed дочерних задач. Сохранить историю и запросить необходимые факты.
- Существующий arrived без entry_at: показать уточнение даты, не создавать событие и не возвращать к будущей подготовке.
- Старый подтвержденный документ/факт завершения сохранить, если смысл и эпизод совпадают. Не терять результаты из reported_fact.
- Новый въезд/адрес создает предусмотренный движком эпизод и recheck. Не стирать старые результаты и не переносить регистрацию на новый адрес автоматически.
- Исправление/отмена должно пересчитывать зависимые задачи и сохранять независимые. Snapshot undo из макета не применять к production.
- Повтор запроса с тем же idempotency key не создает второй результат/outbox. Ошибка доставки не откатывает сохраненный маршрут.
- Session draft онбординга версионировать; старый черновик безопасно восстановить либо предложить недостающие поля, не теряя введенное.

## Очередность работ и точки входа

1. `models.py`, `engine.py`, `catalog.py`, `service.py`, при необходимости `db.py`/responses/OpenAPI: контракт, миграция, семантические процессы, eligibility и progress.
2. Каталог обоих вузов: содержательные карточки/источники, локальные условия, demo overrides. Существующие нормы не редактировать глобально.
3. `student.js`: адаптивные вопросы, формы результатов, точечные уточнения, подтверждение и идемпотентное сохранение.
4. `student-ui.js`, `roadmap-view.js`: отображение статусов/декомпозиции/будущих задач, существующий Hero, возврат и история. CSS изменять только для размещения новых состояний в текущей системе.
5. Обновить тесты и документацию; проверить MAX отдельно. Не переносить синтетический порядок Hero из макета (в частности, жесткое первенство даты визы).

Граница объема: реализовать новую подготовку и поздний вход; сохранить и регрессионно проверить существующие повторные события/продления. Создание новых интеграций с вузами/МВД, хранение сканов, универсальный юридический помощник и новый дизайн не входят.
