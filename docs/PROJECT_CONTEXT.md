Срез: 28.09.2026. Это вводная к проекту и его текущему состоянию, а не новая продуктовая спецификация. Изменения после этой даты нужно подтверждать новым отчётом команды. Документ подготовлен для коллеги, который будет использовать материалы как источники ChatGPT-проекта.

## 1. Что строим

«Рядом» — mini-app и бот в MAX для иностранных студентов СПбГУПТД и ЛЭТИ. Приложение собирает персональный план документов, обращений и процедур из профиля студента, записанных им событий и версий правил. Несколько действий идут параллельно; новый адрес, въезд или документ пересчитывает соответствующую часть плана и сохраняет историю.

MarketKit — команда проекта. Название продукта — «Рядом»; это не основной коммерческий сервис market-kit.ru.

## 3. Состав MVP

Первый проход: язык → вуз → режим въезда → дата въезда → жильё → окончание визы при наличии → согласие → первый план. Неизвестный ответ допустим. Дополнительные обстоятельства уточняются в «Мои данные».

План имеет разделы «Сейчас / Скоро / Позже / История». У действия есть объяснение применимости, документы, контакт, источники, версия правила, пользовательский статус и отдельные временные значения. Приложение не просит загрузить документы.

| Семейство | Смысл |
|---|---|
| M01 | Подготовка к приезду / приглашение |
| M02 | Проверка документов въезда и миграционной карты |
| M03 | Обращение в университетский офис после приезда |
| M04 | Миграционный учёт по фактическому месту проживания |
| M05 | Первичное медицинское освидетельствование |
| M06 | Дактилоскопия и фотографирование |
| M07 | Заблаговременная подача документов для продления визы |
| M08 | Подготовка продления учёта |
| M09 | Изменение обстоятельств; оркестрация и отдельное review-действие при необходимости |
| M10 | Повторное медицинское освидетельствование |

Десять семейств не означают десять обязательных карточек у каждого студента. M09 не должен дублировать M03/M04. Состав зависит от фактов и применимости.

События включают въезд/повторный въезд, смену жилья, получение визы, подтверждение регистрации, медосмотр, дактилоскопию, гостиницу, замену паспорта, изменение миграционного/учебного статуса. Не все такие ситуации автоматизированы юридически: часть вызывает проверку в офисе. Событие сохраняется после подтверждения; ошибку можно исправить или отменить с сохранением истории.

Редактор вуза работает только со своими локальными правилами: черновик → проверка → preview затронутых планов → явная публикация новой версии → пересчёт и уведомления. Правовой каталог не редактируется этой ролью. Роли сотрудников в прототипе модельные; подключения к внутренним системам двух вузов нет.

## 5. Важные смысловые ограничения

1. **Заполненный профиль не подтверждает закон.** Возраст/гражданство/даты — входные факты студента, а не проверенные договорные исключения. При отсутствии пользовательских полей используется `conditional`; при непроверенной правовой применимости — `needs_review`.
2. **Сроки имеют разный смысл.** Государственный срок, обращение в вуз, начало подготовки и окончание документа хранятся отдельно с владельцем, единицей и источником. Вузовская рекомендация не является федеральным сроком.
3. **Нельзя додумывать единицу.** В MVP «45 дней» ЛЭТИ и «2 дня» СПбГУПТД остаются текстом без точной даты. Нет подтверждённого рабочего календаря и графика офиса для произвольных вычислений.
4. **Федеральные даты пока не персонализированы.** Нет проверенного каталога гражданств/договорных исключений. Персональные 7 рабочих дней, 30/90 календарных дней и повторный медсрок не вычисляются как установленные обязанности. Исследование содержит базовые нормы и вопросы для проверки; это не готовое заключение для каждого студента.
5. **Подтверждённые локальные даты могут считаться независимо.** Пример СПбГУПТД: рекомендованное обращение за 60 календарных дней до окончания визы; за 50 дней — для продления регистрации в общежитии. Второе не переносится на частный адрес или другой вуз.
6. **Статус пользователя и статус движка независимы.** «Выполнено» — отметка студента, а не решение МВД/вуза. После события прежнее действие может требовать проверки или перейти в историю с сохранённым статусом.
7. **LLM не управляет правилами.** Она предлагает тип события и язык; человек выбирает/подтверждает факты в форме. Юридический чат, генерация норм и автоматическое изменение плана моделью не реализованы.
8. **Не заявлять отсутствующие интеграции.** Нет МВД, ЕСИА, университетских информационных систем, официального автоматического подтверждения процедур или автоматического мониторинга законодательства.

## 6. Данные и архитектура простыми словами

Backend: Python 3.11, FastAPI, строгие Pydantic-модели. Одна SQLite/WAL-база в постоянном Docker volume; один процесс приложения. Frontend: обычные JS/CSS, без React и отдельной сборки. Docker, OpenAPI 3.1 и DATA-API.yaml подготовлены.

Профиль хранится на сервере. При настоящем запуске backend проверяет подпись MAX initData и связывает пользователя с MAX ID. MAX не передаёт автоматически гражданство, сроки документов и учебный статус: студент сообщает их сам. В браузере хранится сессионный токен, а не весь профиль.

События накладываются на исходный профиль и дают эффективные факты; движок собирает план, сервис сравнивает его с прежним, сохраняет историю и очередь уведомлений. Сбой отправки MAX не отменяет сохранённый план. Повторные операции защищены от дублей.

Браузерное демо имеет независимых вымышленных студентов и переключатели в «Мои данные». Их планы считает тот же движок; это не зашитые готовые маршруты. На настоящем MAX-аккаунте кнопок переключения нет. Закрытая вкладка может потерять доступ к токенам демо; демо не является способом связать реальный аккаунт.

Сканы, паспортные номера, точный адрес, диагнозы и медицинские заключения не собираются. Хранятся минимальные обстоятельства, даты, факты процедур, статусы и история. Комплект для аналитики не содержит базы студентов, настоящих идентификаторов, токенов, ключей, SSH-доступов и закрытого служебного слайда.

## 7. Что полезно делать коллеге

- Сверять формулировки UI/презентации с MASTER FINAL, исследованием и официальным кейсом; находить расхождения, а не автоматически менять утверждённый scope.
- Выполнить RU/EN вычитку: рабочие/календарные дни, recommendation/requirement, обращение/получение результата, неизвестная применимость.
- Проверить доказательность презентации: реализовано ≠ проверено; принято API ≠ получено; два вузовских адаптера ≠ интеграция с вузами; гипотеза эффекта ≠ измеренный эффект.
- Подготовить вопросы офисам/юристу по P0 исследования и план проверки пользовательской ценности.
- Подготовить структуру и тексты финальной презентации, вопросы жюри, краткие ответы и сценарий демонстрации.
- Проверить комплект сдачи по двум официальным PDF и SUBMISSION_CHECKLIST, учитывая новые объявления организаторов отдельно от этого snapshot.

При ревью использовать таблицу: **утверждение / источник и раздел / статус подтверждения / расхождение / предлагаемая правка / вопрос команде**. Для внешнего исследования записывать URL первоисточника, дату проверки, период/редакцию и ограничения. Новые сведения не становятся автоматически новым правилом приложения.

Не придумывать пилоты, интервью, отзывы, измеренное снижение ошибок или нагрузки, число пользователей и договорённости с вузами. В статистике исследования различаются поток принятых и общий контингент, периоды и уровни обучения; известное расхождение численности СПбГУПТД нельзя скрывать. Результаты нового CustDev добавляются только после реальной работы.

Карта кода помогает понять устройство, но не заменяет исходники. Для проверки конкретной функции запросить соответствующий файл у разработчика; не объявлять отсутствие/наличие поведения только по краткому описанию модуля.
