# MAX Hackathon — быстрый гайд по боту и mini-app

**Дата:** 27.09.2026  
**Для проекта:** MAX Foreign Students  
**Назначение:** быстро разобраться именно с доступами и подключением к MAX до начала основной разработки.  

> Важно: этот документ описывает платформенную часть MAX для хакатона. Продуктовый scope и архитектуру брать из `max_foreign_students_developer_handoff_MASTER_FINAL_2026-09-27.md`.

## 1. Самое главное: бот уже создан организаторами

Для этого хакатона **не нужно создавать нового бота через «MAX для партнёров»**.

Команде выдан **токен уже созданного бот-аккаунта**. Именно поэтому в FAQ организаторов используется формулировка «выданный бот».

Токен даёт **технический доступ к Bot API** этого бота: можно получать информацию о боте, принимать события, отправлять сообщения, кнопки, медиа и т. д.

Токен **не даёт административный доступ** к карточке бота в «MAX для партнёров»: участники не могут самостоятельно менять название, ник, логотип и другие недоступные через API настройки. Если понадобится административная настройка — обращаться к организаторам.

### Что это значит для капитана

Никакого отдельного действия «получить доступ к созданию бота» делать не надо. Доступ уже выдан токеном. Бота заново создавать нельзя и не нужно.

---

## 2. Нужны ли юрлицо / ИП / самозанятость

### Для обычного самостоятельного запуска в MAX

По общей документации MAX подключение к «MAX для партнёров» доступно российским:
- юридическим лицам;
- ИП;
- самозанятым.

Обычное физлицо без такого статуса сейчас не проходит верификацию для самостоятельного создания ботов/mini-app через партнёрскую платформу.

### Для этого хакатона

**Нет, команде не нужно оформлять юрлицо, ИП или самозанятость и не нужно регистрироваться в «MAX для партнёров».**

Организаторы уже создали бот и выдали команде токен. Для mini-app действует специальная процедура хакатона: команда передаёт организаторам публичную HTTPS-ссылку, а они сами привязывают её к выданному боту.

Специальный порядок хакатона здесь важнее общей инструкции MAX для владельцев обычных ботов.

## 3. Первые 5 минут: проверить токен и узнать имя бота

Не вставлять токен прямо в код. Положить его в `.env`:

```env
MAX_BOT_TOKEN=...
```

Проверка:

```bash
curl -X GET "https://platform-api2.max.ru/me" \
  -H "Authorization: $MAX_BOT_TOKEN"
```

В ответе будет информация о боте, включая `username`. По этому username бот находится в MAX.

**Важно:** с 2026 года использовать домен `platform-api2.max.ru`, а не старый `platform-api.max.ru`.

После получения username:
1. открыть MAX обычным пользовательским аккаунтом;
2. найти выданного бота;
3. открыть диалог;
4. проверить, что backend получает событие запуска/сообщения и отвечает.

---

## 4. Как технически оживить выданного бота

Минимальная схема:

```text
Пользователь MAX
    ↓
Выданный бот
    ↓ события
Backend команды
    ↓ API-запросы
MAX Bot API
```

### Получение событий

Для разработки можно использовать:
- Webhook;
- Long Polling.

Для рабочего решения MAX рекомендует Webhook.

Webhook должен:
- быть доступен по `https`;
- работать на стандартном HTTPS-порту 443;
- иметь доверенный TLS-сертификат, не self-signed;
- отвечать `200 OK` максимум за 30 секунд.

Пример подписки:

```bash
curl -X POST "https://platform-api2.max.ru/subscriptions" \
  -H "Authorization: $MAX_BOT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://YOUR_DOMAIN/webhook",
    "update_types": ["message_created", "bot_started"],
    "secret": "YOUR_WEBHOOK_SECRET"
  }'
```

На сервере проверять заголовок `X-Max-Bot-Api-Secret`, если `secret` задан при создании подписки.

### Что бот должен уметь минимум

Для проекта достаточно, чтобы бот уверенно:
- реагировал на старт;
- показывал короткое onboarding-сообщение;
- давал кнопку открытия mini-app;
- присылал уведомления о значимых изменениях roadmap;
- умел вернуть пользователя в нужный экран/шаг.

Основная сложная визуальная часть продукта может жить в mini-app.

## 5. Mini-app: что это на самом деле

Mini-app в MAX — это обычное веб-приложение на HTML/CSS/JavaScript, открываемое внутри MAX и **привязанное к чат-боту**.

Отдельно от бота mini-app в MAX не существует.

Для разработки можно использовать React, но это не обязательное требование хакатона.

### Что нужно сделать разработчику

1. Создать frontend mini-app.
2. Проверять его локально в браузере.
3. Разместить frontend на публичном HTTPS-хостинге.
4. Получить URL вида, например:
   `https://app.example-host.ru`
5. Проверить URL с телефона и компьютера вне локальной сети.
6. Передать URL организаторам через форму хакатона:
   `https://sbor-ssylok-dlya-mini-prilojeniy.testograf.ru/`
7. Дождаться, пока организаторы привяжут mini-app к выданному боту.
8. После привязки открыть чат с ботом в MAX — в нём должна появиться кнопка запуска mini-app.
9. Проверить сценарий и в мобильной, и в веб-версии MAX.

### Собственный домен

Не нужен. Подойдёт публичный HTTPS-адрес хостинга.

## 6. Почему общая документация MAX может запутать

В обычной ситуации владелец бота заходит в «MAX для партнёров» → `Чат-боты` → `Настройки` и сам вставляет URL mini-app.

**На хакатоне делать так не надо и доступа к этим настройкам у команды нет.**

Специальный FAQ хакатона прямо говорит:
- зарегистрироваться в «MAX для партнёров» не нужно;
- HTTPS-ссылку mini-app надо отправить организаторам;
- привязку выполняют организаторы;
- административных прав на выданного бота у участников нет.

## 7. Авторизация пользователя внутри mini-app

При открытии mini-app MAX передаёт стартовые данные через `window.WebApp` / `WebAppData`.

### Нельзя

Не использовать `initDataUnsafe` как доказательство личности пользователя: этот объект удобен для чтения, но сам по себе не является доверенным источником.

### Нужно

Передавать `initData` / `WebAppData` на backend и валидировать подпись сервером с использованием токена бота по официальному алгоритму HMAC-SHA256.

Только после успешной проверки связывать MAX user id с пользовательским профилем/roadmap.

Для данного проекта это особенно важно, потому что состояние студента должно сохраняться между ботом и mini-app.

## 8. Deep links

После того как mini-app привязан к боту, можно открывать его напрямую с параметром:

```text
https://max.ru/<botName>?startapp=<payload>
```

Это пригодится для уведомлений вроде:

> «Ваш roadmap изменился — открыть новую задачу»

В `payload` можно передать идентификатор экрана/задачи, а mini-app при запуске откроет нужную карточку.

Не делать deep links обязательными для первой версии: сначала добиться стабильного открытия mini-app через кнопку в боте.

## 9. Что делать с токеном

Токен — секрет с прямым доступом к выданному боту.

### Обязательно

- хранить только в переменной окружения / secret storage;
- иметь `.env.example` без значения;
- добавить `.env` в `.gitignore`;
- не коммитить токен в Git;
- не вставлять его в screenshots/README/публичные issue;
- не логировать его в CI/CD.

Если токен случайно был опубликован вне команды, участники не имеют административного доступа для самостоятельного управления карточкой бота — нужно сразу связаться с организаторами через `support@hackathon-max.vk.company`.

Токен на скриншоте из письма **не нужно копировать в этот документ или в репозиторий**.

## 11. Предлагаемый порядок работы команды

### Фаза A — MAX smoke test

Цель: доказать, что доступы работают.

```text
токен → GET /me → бот найден в MAX → событие приходит backend → бот отвечает
```

### Фаза B — mini-app smoke test

```text
простая страница → HTTPS → форма организаторов → привязка → mini-app открывается внутри MAX
```

### Фаза C — связать пользователя

```text
MAX initData → server validation → MAX user id → профиль в БД
```

### Фаза D — подключить продукт

```text
профиль + события → rules engine → roadmap → mini-app → уведомления в боте
```

Так платформа проверяется отдельно от сложной предметной логики, и проблемы доступа не смешиваются с проблемами rules engine.

## 12. Что НЕ делать

- Не создавать новый бот вместо выданного организаторами.
- Не пытаться регистрировать команду в «MAX для партнёров» ради этого хакатона.
- Не оформлять юрлицо/ИП/самозанятость только ради доступа к выданному хакатонному боту.
- Не ждать отдельный «ключ mini-app»: отдельного API-токена mini-app не требуется.
- Не считать токен административным доступом.
- Не пытаться самостоятельно менять ник/название/логотип выданного бота на онлайн-этапе.
- Не хранить токен во frontend mini-app: он должен оставаться только на сервере.
- Не доверять `initDataUnsafe` для аутентификации.
- Не оставлять mini-app только на localhost — внутри MAX нужен публичный HTTPS.
- Не строить production на Long Polling, если можно поставить Webhook.

## TL;DR для коллеги

**У нас уже есть готовый бот от организаторов. Токен — это ключ к его API, а не право создать/администрировать бота. Для хакатона юрлицо/ИП/самозанятость не нужны и в «MAX для партнёров» регистрироваться не надо. Mini-app — обычный HTTPS web-app: мы его хостим, отправляем URL через форму, а организаторы привязывают к выданному боту. После этого проверяем запуск внутри MAX, серверно валидируем initData и только затем подключаем основной backend/rules engine.**
