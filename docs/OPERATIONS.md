# Сохранение данных и резервные копии

27.09.2026. Один FastAPI-процесс и SQLite/WAL в volume `max-students_max_data`. `docker compose stop` / `up -d` сохраняют данные. `down -v` удаляет volume; для обычного обновления не использовать.

Из `/opt/max` создать согласованный приватный снимок работающей базы:

```sh
docker compose exec -T app python -m app.operations backup /app/data/backups/release-2026-09-27.sqlite3
docker compose exec -T app python -m app.operations verify /app/data/backups/release-2026-09-27.sqlite3
```

Используйте новое имя для каждого снимка: существующий файл никогда не перезаписывается. CLI допускает только `.sqlite3` внутри `backups` рядом с настроенной базой, проверяет SQLite integrity и наличие таблиц приложения. Снимок создаётся через SQLite backup API, включает зафиксированные WAL-данные и получает права 0600. Не копируйте один live `.sqlite3` при продолжающихся записях.

Снимки содержат личные данные и сессии; они остаются в приватном volume, не в репозитории, архиве кода или публичном web root. Результат CLI содержит только количества строк. Перед пилотом установить согласованный срок хранения/удаления резервных копий: удаление профиля из рабочей базы не переписывает исторические снимки. В текущей тестовой среде снимки создаются оператором вручную; расписание backup не заявлено.

Восстановление сначала проверять в отдельной базе и изолированном экземпляре приложения с `BOT_TRANSPORT=disabled`, пустым токеном MAX и без публичного доступа. Запуск snapshot меняет его содержимое (миграции/worker), поэтому работать на дополнительной копии. Сопоставить план, события, статусы, версии и очередь. Сценарий проверен автоматическим тестом `tests/test_persistence.py`.

Автоматического live restore в CLI нет. При настоящем восстановлении необходимы остановка единственного writer, отдельная копия текущего volume, проверка пути и согласованная замена всей базы с её WAL/SHM. Нельзя подменять `.sqlite3` при активном процессе или переносить старый WAL поверх восстановленной базы. Возобновлять транспорт MAX только после проверки состояния очереди; физический дубль после неоднозначного сетевого ответа MAX остаётся известным ограничением.

При обновлении тестового сервера пересобирайте только `app`. Существующий временный tunnel не пересоздавать. Параметры и команды: `DEPLOYMENT.md`.
