### A01 — P1: медицинский шаг противоречит своему состоянию

Исправлено в `a0f2c49`, проверено локально и на публичном сайте 23.10.2026. Ниже исходное наблюдение аудита 22.10: остаточный дефект C01, не новая регрессия.

В demo + prototype_timing для M05/M06/M10 в `conditional`/`needs_review` основная инструкция предлагает сначала уточнить необходимость процедуры. При этом заголовок «Пройти…», подпись «Выполнить до» и ожидаемый результат прохождения выглядят как персональное требование, а доступный результат — только «Вопрос отправлен». Сервер не вычисляет неподтверждённую дату и не записывает процедуру выполненной; дефект относится к смыслу экрана.

Воспроизведение: синтетическая задача указанного семейства/состояния → План → раздел → действие → сопоставить заголовок, срок, инструкцию, ожидаемый результат и кнопку; для `needs_review` открыть уточнение в отделе. Повторить в обоих вузах, RU/EN.

Критерий закрытия: весь персональный шаг описывает уточнение; общий интервал явно условен. В actionable-ветви сохраняется прямое действие. Отправленный вопрос и полученный ответ не становятся выполненной процедурой, в том числе после reload.

## Как работают следующие чаты

1. **Начало.** Проверить Git по действующим инструкциям, прочитать эту сводку и нужную часть [CODE_MAP.md](CODE_MAP.md). Определить порученный результат и затрагиваемые ID. Старые PASS относятся только к своей версии и условиям.
2. **Изменение.** Один логически связанный пакет передавать отдельным коммитом после подходящих проверок. Во время ревью дерево не менять; параллельную работу вести в отдельной рабочей копии. При намеренном ревью незакоммиченных изменений зафиксировать базовый SHA, diff и хеши проверяемых файлов, явно назвать это исключение.
3. **Проверка.** Проверять ожидаемое поведение независимо от реализации, в том числе отсутствие прежней ошибки. Для текстов пройти затронутые поверхности сценария: План → раздел → действие → уточнение/справка → результат/история, где применимо. Взять обе локали и затронутые вузы/режимы, проблемное состояние и нормальный контрольный вариант. Не требовать полного аудита приложения для каждой редакторской правки. Автотесты и смысловая проверка экрана имеют отдельные результаты.
4. **Передача.** Обновить затронутые строки здесь: `открыто` → `реализовано, ожидает проверки` → `проверено на <SHA и условиях>`; при остатке — `частично`. Записать commit исправления и доказательства. Если сама задача только read-only, вернуть готовую поправку статуса в отчёте; её переносит следующий пишущий чат. Один автор записи на одну рабочую копию.
5. **После выкладки.** В рамках порученной проверки сверить идентификатор реально запущенной сборки и конфигурацию режима, затем пройти короткий набор затронутых критичных сценариев. Если версия недоступна для проверки, явно записать это ограничение. Push и локальный PASS не заменяют проверку сервера. Выкладку выполняют только по прямому поручению пользователя.

Короткую передачу готовит завершающий чат, без требования к пользователю заполнять форму:

```text
Задача: что изменить или проверить; ID замечаний.
Версия: исходный SHA → кандидат SHA; ветка и состояние дерева.
Ожидаемое поведение: кратко, включая то, что должно сохраниться.
Проверено: сценарии, среда/режим, результат и доступные доказательства.
Осталось: открытые ID, NOT RUN, неподтверждённые предположения.
Следующий шаг: конкретное действие в пределах поручения.
```

Правила помогают заметить пропуски, но не гарантируют отсутствие дефектов и не являются настроенной CI-блокировкой. Основа подхода: [GitHub — решения и история ревью](https://docs.github.com/en/pull-requests/reference/pull-request-reviews), [OpenAI — короткие предметные правила рядом с кодом](https://developers.openai.com/blog/custom-code-review-rules-for-codex). Конкретная сводка и шаблон — адаптация к этому проекту.
